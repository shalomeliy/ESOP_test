# ESOP Enterprise Engine & Testbed

מערכת מלאה לניהול, תרגול וסימולציה של חלוקת אופציות/RSU, התאמת מיסוי (ישראל 102/ארה"ב ISO/NSO), ניהול נאמנים וסטטוסי עובדים.

## 🚀 איך מריצים את המערכת במחשב חדש (מדריך פשוט לכולם)

חושבים על זה ככה, כמו לפתוח חנות צעצועים חדשה: קודם בונים את המדפים (מתקינים תוכנות),
אחר כך ממלאים אותם בצעצועים (מכינים בסיס נתונים), ורק אז פותחים את הדלת ללקוחות (מדליקים
את השרת). כל שלב פה צריך לקרות פעם אחת בלבד במחשב חדש, חוץ משלב 4 (הדלקת השרת) שחוזרים
עליו בכל פעם שרוצים להשתמש במערכת מחדש.

### שלב 0: מה צריך שיהיה כבר מותקן במחשב
- **Python** גרסה 3.11 ומעלה — זו השפה שהתוכנה כתובה בה. אפשר לבדוק מה יש עם `python --version`.
- **Git** — כדי להוריד את הקוד.

### שלב 1: מורידים את הקוד למחשב
```bash
git clone <כתובת-הריפו-שלכם>
cd ESOP_test
```

### שלב 2: מתקינים את מה שהתוכנה צריכה כדי לרוץ
בדיוק כמו לקנות את כל חומרי הגלם לפני שמתחילים לבשל מתכון:
```bash
pip install -r requirements.txt
```

### שלב 3: בונים ומכינים את בסיס הנתונים (פעם אחת בלבד!)
במחשב חדש עדיין אין שום בסיס נתונים — צריך לבנות אותו מאפס. בסיס נתונים הוא כמו ארון עם
המון תאים ריקים; הפקודה הזו בונה את כל התאים (הטבלאות):
```bash
alembic upgrade head
```
לפני שממלאים אותו בדוגמאות — יש בקוד גם הודעות בעברית, וב-Windows המחשב לפעמים לא יודע
לקרוא עברית בטרמינל אם לא אומרים לו איך. אז קודם אומרים לו "תקרא הכל כ-UTF-8":

בטרמינל של PowerShell (ברירת המחדל ב-Windows):
```powershell
$env:PYTHONIOENCODING = "utf-8"
```
בטרמינל של bash / Git Bash / מק / לינוקס:
```bash
export PYTHONIOENCODING=utf-8
```

ועכשיו ממלאים את הארון בדוגמאות לתרגול — חברות, עובדים, מענקים מדומים, הכל לצורך בדיקה בלבד:
```bash
python -m backend.seed_data
```

## 🗄️ מיגרציות סכמה (Alembic)

מ-v0.4.0 סכמת ה-DB מנוהלת ב-Alembic. הסיבה: `Base.metadata.create_all()` יוצר רק טבלאות
חסרות ולעולם לא מוסיף עמודה לטבלה שכבר קיימת — בדיוק זה גרם בעבר לקריסות `no such column`
מול `esop_database.db` הקיים.

כל הפקודות מורצות **משורש הפרויקט** (שם נמצא `alembic.ini`).

### הצעד החד-פעמי על `esop_database.db` הקיים

**חובה להריץ `alembic stamp head` — ולעולם לא `alembic upgrade head`.**

אם ה-`esop_database.db` שלכם נבנה לפני שהפרויקט עבר ל-Alembic (`create_all` ישן),
הטבלאות הבסיסיות כבר קיימות בו, ולכן `upgrade` ינסה ליצור אותן שוב וייפול מיד על
`table companies already exists`. `stamp` רק רושם את מספר הרוויזיה בטבלת
`alembic_version` בלי להריץ שום DDL — כלומר "ה-DB הזה כבר נמצא ב-baseline".

```bash
alembic stamp head    # פעם אחת בלבד, על DB קיים
alembic current       # אימות: צריך להציג את אותו מזהה כמו `alembic heads` (ראו למטה) - לא מספר קבוע, הוא משתנה עם כל מיגרציה חדשה
```

אחרי ה-stamp, `alembic upgrade head` הופך לבטוח ולא עושה כלום עד שתתווסף רוויזיה חדשה.

### DB חדש לגמרי (מפתח חדש / סביבת בדיקות)

```bash
alembic upgrade head          # בונה את כל הטבלאות מאפס (המספר גדל עם כל גרסה - ראו migrations/versions/)
python -m backend.seed_data   # נתוני דמו (אופציונלי)
```

### הוספת מיגרציה חדשה

```bash
alembic revision --autogenerate -m "add xxx to yyy"
# חובה לקרוא את הקובץ שנוצר לפני ההרצה: autogenerate לא מזהה שינוי שם עמודה
# (הוא יציע DROP + ADD ויאבד נתונים) ולא מזהה שינוי ב-CHECK constraint.
alembic upgrade head
alembic downgrade -1          # rollback לרוויזיה הקודמת
```

### עבודה מול DB אחר (בדיקות, ניסויים)

`ESOP_DATABASE_URL` גובר גם על האפליקציה וגם על Alembic. בלי המשתנה — ברירת המחדל היא
`sqlite:///./esop_database.db` כמו תמיד. אף פעם אל תנסה מיגרציה חדשה ישירות על ה-DB החי:

```bash
ESOP_DATABASE_URL="sqlite:///./scratch.db" alembic upgrade head
```

### בדיקת דריפט בין `models.py` ל-DB

```bash
alembic revision --autogenerate -m probe   # הגוף של upgrade() חייב להיות pass
```

אם נוצרו פקודות — יש דריפט בין המודלים לסכמה בפועל, וצריך לטפל בזה לפני כל דבר אחר.
בכל מקרה למחוק את קובץ ה-probe בסוף, הוא לא אמור להיכנס ל-git.

> `alembic.ini` חייב להישאר ASCII בלבד: Alembic קורא אותו בקידוד ה-locale של המערכת
> (cp1252 כאן), ולכן הערה בעברית שם מפילה כל פקודת alembic ב-`UnicodeDecodeError`.
> ההסברים בעברית יושבים ב-`migrations/env.py`, שנקרא כ-UTF-8.
